# SecondU：完整产品方向与当前原型体验

SecondU 是以个人数字分身为核心的智能体产品。SecondU 持续理解你的背景、经历、偏好、关系和目标，在不同任务、场景和设备之间延续这些理解。组织归拢零散多模态信息，调度合适的专家与工具，主动处理任意想法与事务，并支持协作、社交和专业服务。

三个重点价值：

- 减少背景信息和既有判断的重复输入。
- 让完整的多模态上下文在设备和场景之间连续流转。
- 将经过授权、适当脱敏的个人专业能力分发出去，支持 Agent 之间的协作、社交和交易。

这三项价值用于说明重点，不限制产品的完整范围。[产品定位](PRODUCT.md) 描述完整形态，[产品路线](ROADMAP.md) 说明阶段、当前基础与验收条件。本文的体验步骤和验证证据对应当前可运行原型；跨设备连续体验、专业服务、社交与 A2A 交易的完整形态不等同于已交付能力。

## 产品判断

当模型越来越能执行任务，用户仍需要在不同会话里反复解释自己：哪些事情已经决定，什么约束不能变，谁参与过，上一版为什么被否定。一次回答可以完成得很好，下一件事却经常从头开始。

我认为个人 Agent 的产品机会在于建立一个由用户掌握、不断更新的个人主体。任务和工具围绕这个主体组织：理解来自哪里、这次用了哪些背景、哪些内容应该修正、交付怎样接着使用，都应当成为用户能操作的对象。

这也是 SecondU 采用“数字分身 + 专业 Agent”的原因。数字分身维持对本人的理解；专业 Agent 按职责参与任务。用户可以直接对话，也可以组织一个有负责人的小团队，看清分工、执行和交付。

## 五分钟体验主线

先打开中文或英文虚构示例，浏览个人画像、来源与专家团队。重点观察个人理解如何进入任务、如何被纠正，并延续到下一件事。首次建立自己的分身时，可在个人空间导入已有摘要，逐条修正并确认，再直接带入可编辑任务。

| 时间 | 操作 | 核对的证据 |
| --- | --- | --- |
| 0:00–1:00 | 选一条已确认偏好或现实约束，展开来源 | 原文、确认状态、版本，避免把推测当事实 |
| 1:00–2:00 | 提出具体任务，查看本轮使用的个人背景；明确哪一项背景应改变方案 | 选中的条目、适用范围、来源摘录，以及答复中对应的取舍 |
| 2:00–3:00 | 打开「纠正个人理解」，说明偏差与适用情境；保存候选后本人确认 | 原答复与纠正并存，新认知的版本和确认动作 |
| 3:00–4:00 | 新建相关任务，不重新粘贴已确认的纠正 | 新任务是否选中修订后的理解，是否仍使用旧说法 |
| 4:00–5:00 | 打开任务成果、编辑并保存一版，再回看原版本 | 实际文件、版本差异、原件下载；与上下文证据分别核对 |

网页与桌面示例可体验界面和保存行为，不会调用模型或操作真实账号。要取得“背景改变判断”的模型证据，需要在个人空间连接模型，用合成材料实际运行第二步与第四步。[个人上下文对照](CONTEXT-BENCHMARK.md)已保存 4 个合成案例、28 项离线契约检查、冻结输入和 12 次真实模型回答，可复查持续偏好纠正、单次例外与新任务迁移。

辅助查看：群聊设置可选择成员、负责人和协作方式；构建过程展示真实提交、设计取舍、验证记录与原文。完整说明分别见 [Harness](HARNESS.md)、[个人记忆导入](MEMORY-IMPORT.md) 和 [通信接入](COMMUNICATIONS.md)。

## 运行真实任务

按 [启动说明](../QUICKSTART.md) 安装 Node.js 22.18+、依赖并构建。模型执行需要本机 Codex CLI，模型 Key 在应用内由使用者配置；没有 Key 时会明确停在配置状态。仓库、应用包与示例均不提供开发者凭据。

可用以下公开、无私人资料的任务检查文件闭环：

> 请创建一份活动准备清单 Markdown 文件。活动是一次 6 人读书会，预算上限 300 元，周六下午 2 点开始。列出准备事项、负责人待确认项和预算表；不要购买、发消息或联网。完成后说明哪些条件仍需确认。

随后把人数改为 8 人，要求检查预算并更新文件；再从成果区编辑一处文字、保存新版本、重新打开。这里应核对真实文件、任务记录和版本变化，不能只看助手是否说“完成”。具体提供方对工具协议的支持与输出质量需单独检查。

## 当前证据与限制

个人上下文已有一轮公开的合成对照：4 个案例、3 种输入条件，共 12 次真实模型回答，覆盖持续偏好纠正、单次例外和后续任务迁移。结构化上下文与完整原文均作出 A/B/A/E 的选择；结构化输入另外排除了未确认和无关条目，并在 4 次回答中保留有效事实引用。这支持版本、范围和可追溯性的检查，不构成回答质量优于原文或节省 token 的结论。可直接查看[输入、原始回答与可视化对照](../benchmarks/results/2026-10-01/review.html)及[实验条件](CONTEXT-BENCHMARK.md)。

一次真实 DeepSeek 最小团队任务已完成“负责人委派一名专家 → 等待回传 → 汇总”，使用真实 Codex 运行时，共 4 次模型请求；任务和执行树重开后仍保留。这个合成算术任务验证的是执行通路，不证明复杂协作质量或通用能力。

原始文件、版本、消息修改分支、表情、可纠正的背景展示分别有接口或界面验证。完整更新记录见 [构建过程](DEVELOPMENT.md)，设计与实现见 [Harness](HARNESS.md)。每条证据均保留对应范围。

桌面实屏已核对三种 Office（DOCX、XLSX、PPTX）的本机 PDF 预览、DOCX 历史版本、消息编辑分支，以及成果工作区的调宽、展开、Escape 还原和草稿保留。工牌可通过键盘翻面并保留可见焦点。应用包另有运行时、构建指纹、静态资源、原件下载和本机签名检查，具体版本及证据见 [最新交付核对](DEVELOPMENT.md#2026-10-01-发布前文档与应用包核对)。

当前仍是可运行原型：本机服务在线时才能执行定时任务；实际远端主机、真实外部账号、跨设备传输和长期认知质量尚需独立验证。市场、Dating、设备场景和部分资源功能明确标注 Dev。Office 预览需要本机 LibreOffice，缺少时仍可下载原件；macOS 本地包采用临时签名，尚未 Apple 公证。

下一步需要验证：与普通对话使用同一份材料、同一个任务时，用户重复补充背景的次数、关键约束遗漏、修正后能否迁移到下一次任务。尚未完成这组用户实验，也没有编造效率提升比例。
