# Shared API contract

Default local API: 127.0.0.1:58645. JSON. GET bootstrap returns `Bootstrap` from shared/contracts.ts, never secrets. Errors use `{error: string, code?: string}` with a non-2xx status. All writes persist before responding. Frontend refreshes bootstrap after mutations and polls active tasks. Backend implementation may add fields but coordinate breaking changes.

- `GET /api/health` application identity and version; `GET /api/bootstrap`
- `POST /api/tasks` CreateTask -> Task (create queued; separate run). `GET /api/tasks/:id` -> Task
- `POST /api/tasks/:id/run` -> Task. `POST /api/tasks/:id/message` `{content}` -> Task (continues/steers with user correction). `POST /api/tasks/:id/cancel` -> Task. `POST /api/tasks/:id/approval` `{approvalId, decision:'approve'|'reject'}` -> Task.
- `PUT /api/artifacts/:id` `{content,baseVersion}` -> Artifact; 409 on stale version. `GET /api/artifacts/:id/download` attachment.
- `POST /api/sources` `{title,kind,text}` -> Source. Import is evidence, not confirmed fact.
- `POST /api/facts` `{kind,statement,sourceIds,status}` -> Fact. `PUT /api/facts/:id` `{statement,status,reason,baseVersion}` -> Fact. Preserve revisions; 409 on conflict. User explicitly confirming a candidate can set confirmed; a model cannot.
- Preference facts may explicitly carry `preferenceDomain: 'work' | 'taste' | 'general'`. Other kinds reject that field. Omitting it on an edit preserves the existing category; changing the kind away from preference removes it. Revision snapshots retain each explicit category. Old uncategorized preferences stay general; the profile does not infer this category from words in the statement.
- `POST /api/people`, `PUT /api/people/:id`; `POST /api/relationships`; `POST /api/events`; `POST /api/goals`, `PUT /api/goals/:id`: entity shape from shared types (server generates id/timestamps).
- `POST /api/agents`, `PUT /api/agents/:id` -> AgentProfile. QR or pasted profile import is a preview first, same create endpoint after user review; URL content is never automatically fetched/executed.
- `POST /api/automations`, `PUT /api/automations/:id`; `POST /api/automations/:id/run` -> Task. Only enabled schedules run while computer/server is online. Source-import triggers are local events.
- `PUT /api/settings/provider` settings plus optional `apiKey` / `clearKey` -> ProviderSettings (masked). `POST /api/settings/provider/test` -> `{ok,message,latencyMs?}`.
- `GET /api/export` downloadable personal data JSON WITHOUT credentials.
- Resource connectors use `authMode: 'none' | 'bearer' | 'oauth'`. OAuth start/status/refresh/disconnect/revoke endpoints are under `/api/connectors/:id/oauth/`; all also follow the selected space API prefix. Credentials never appear in their responses. See [the connector contract](CONNECTORS.md) for exact input fields, callback behavior and account-validation limits.

Runtime: genuine Codex app-server with configurable provider adapters. Production personal spaces create live tasks only; missing keys are explicit needs-configuration, never a silent mock fallback. Showcase spaces contain authored fictional conversations and files for browsing. They do not execute tasks, schedules, model tests, OAuth flows, connector tests, communication commands, or real account operations. Only bundled example project directories can be browsed there. Historical demo tasks in a personal space remain readable and cannot be converted to live execution. The deterministic demo engine remains available only to explicitly constructed test fixtures. Live provider capability validation is separate from these fixtures. Per-task workspace is constrained; arbitrary external writes, terminal/network changes require host approval. A stored approval is not a blanket permission.

Initial seed is fictional: 万叶 (Caspian), a product engineer working on Kimi, with coherent professional and personal records, conversations, milestones, preferences and goals. Authored task examples are already-completed narratives, not simulated running work. No real private identity or messages are used.

## Personal context and task feedback

- Task creation and idle `PUT /api/tasks/:id` accept optional `contextRequest: {domain: 'auto'|'personal'|'project', purpose: 'auto'|'assistance'|'writing'|'planning'|'decision'|'relationship'|'verification', budgetChars: 4000..40000}`. Defaults are auto/auto/20000. Changing this request clears the previous model-thread binding.
- `GET /api/tasks/:id/context` previews the current bounded context. Each enabled task turn records `personal_context`, `context`, and `evidence` events. New assistant messages link to those exact event IDs. Domain/purpose selection uses deterministic terms and explicit references; it is not semantic understanding of the whole archive.
- Context includes relevant confirmed facts and current portrait entries, selected people, recorded relationships/events/goals, and the current project. Records without a confirmation field remain `recorded`. Candidate/inferred claims are excluded from ordinary retrieval and only appear separately for an explicit verification purpose. Source excerpts retain full-source SHA-256, offsets and truncation/omission metadata. Contact lists are never injected wholesale. The structured bundle and serialized evidence have a combined character budget.
- `POST /api/tasks/:id/feedback` accepts `{requestId, messageId?, artifact?: {id,version}, feedback, statement, kind?, preferenceDomain?, scope?: {domain:'personal'|'project'|'any',purpose?,projectId?}, adoption?: {confirmed:true,text}|{confirmed:true,artifact:{id,version}}, outcome?: {text}}`. The original assistant reply or exact artifact revision is read server-side; clients cannot supply replacement originals or hashes. Active tasks reject feedback until the turn ends.
- The feedback transaction preserves task context, original reply/artifact with SHA-256, exact user correction, optional explicit adoption, and optional `user_reported` outcome. It creates one immutable feedback source and a **candidate** fact. Retrying the same request ID/body is idempotent; conflicting content receives 409. Invalid references, credentials, and incomplete adoption confirmation roll back the whole write.
- `GET /api/tasks/:id/feedback` lists task feedback; `GET /api/task-feedback/:id` returns a full snapshot with the current fact status/version. Full records are included in local export, not every bootstrap response. Referenced sources, facts, original tasks and artifacts cannot be deleted while a feedback record depends on them.
- Confirmation remains a separate explicit user action through the existing fact revision endpoint. Future enabled tasks recall the confirmed revision only within its saved scope. This proves persistence and scoped retrieval, not model-quality improvement, automatic retraining or source re-analysis.
- `Bootstrap.executionPolicy` reports `showcase` or `personal` for production entrypoints. The standalone server resolves it from the initial profile; child spaces use a fixed policy independent of later profile edits.
