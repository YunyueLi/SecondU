## 已实现的交互

- 每个空间、每位助理分别保存本次页面会话的示例配置。电脑、邮箱、电话、钱包可以分别进入；关闭再打开仍保留本次内存状态，页面刷新后重置。不写数据库、磁盘、浏览器持久缓存或真实资产。
- 示例电脑可以编辑并保存 `dining-plan.md`，选择列出或阅读示例文件；显示的是本地前端结果，没有执行系统命令。
- 邮箱只接受 `example.com` 示例收件人；填写主题、正文，预览准确内容，返回改稿，确认后显示演示回执。电话使用保留的虚构号码，编辑目的与提纲，返回修订，确认后显示演示回执。不编造收件人或被叫方回复。
- 预算和通信范围可在本次会话编辑；通信范围为逐次确认或仅准备。仅准备时不能生成批准回执；修改范围后必须重新查看邮件／提纲。
- 餐厅码在本地生成，扫描按钮读取固定虚构商家，没有调用摄像头或商家 API。流程包含识别、人数、点餐／排队／只看菜单、菜品份数和总额、预算状态、分工预览、逐次批准和演示回执。
- 点餐超预算时，批准按钮在单次超额确认勾选前禁用；预算内仍需确认。菜单和排队单独处理，排队时间与号码均标明示例。返回改选后保留输入，并对新预览重新确认。
- 回执包含示例编号、处理助理、当前生成时间与演示金额，明确无商家请求、付款、发信或拨号。概览可查看本次演示记录。

所有控件沿用官方 Apps SDK UI；自定义布局是业务组合。中文和英文为显式翻译，用户编辑的示例草稿不自动改写。正文 13px、浮层标题 22px；不用省略号、文字截断或点串占位。

## 正式资源开发计划

1. 定义 `ResourceIdentity` 与 `ResourceGrant`：明确所属空间、助理、资源类型、服务商和可撤销授权；密钥独立存储，不放在角色提示词、名片、导出和普通日志中。
2. 邮件先接真实草稿，再接明确收件人和准确正文的单次发送；电话需单独号码和服务、通话范围及录音规则；支付需具体商家、准确金额、币种和单次审批，不从 Dev 预算迁移真实授权。
3. 外部动作预览绑定资源、目标、内容、版本、金额与有效期。内容修改即失效，执行采用幂等 ID；超时或中断后标记结果未知并查询回执，不能自动重复付款或发送。参考 [OpenMuse 审阅](OPENMUSE-REVIEW.md) 的动作状态机。
4. 真实电脑接管需隔离工作区、可见会话状态、暂停与人工独占控制；现有本机任务目录不等同独立云电脑。餐厅的菜单、排队、订单和付款分别明确接入方，不能凭任意二维码直接授权外部动作。

本轮没有注册账号、购买号码、开通钱包、联系商家、发邮件或拨号，没有调用任何模型服务。Dev 回执不能成为真实交易凭证，Dev 数据不能进入人物事实、外部来源或真实自动化。
