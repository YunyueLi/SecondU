# Reviewed personal context over MCP

SecondU can expose a reviewed snapshot of confirmed personal context to another AI client through a local, read-only stdio MCP server. It uses the official TypeScript SDK, pinned in the root lockfile. It does not start with the application or open an HTTP port.

## Create a grant

In **Settings → Your data → Personal context for other AI apps**:

1. Enter a client name and inspect the confirmed entries in each category. Select only the entries this client needs. Candidates, inferences and superseded records cannot be selected.
2. Optionally include your name (requires a background entry) or source excerpts. Both options are off initially. The name option controls profile metadata; it does not redact names that appear inside a statement you explicitly select. The original imported file, conversation archive, keys and account credentials are not included.
3. Save the grant. It remains **off**. Review its selected categories and count, then acknowledge that the client and its model may read that scope before enabling it.
4. Copy its client configuration into the chosen MCP host. That host starts the stdio process. Disable the grant in SecondU to block its next read.

The client name is an authorization label, not authentication of the calling application. Access rests on the local process and file permissions. The client may send returned context to a remote model according to its own settings. Disabling a grant cannot recall content already received by a client.

A grant freezes the selected records and their revisions. Later imports, confirmations and corrections do not silently expand or replace it. Create a new reviewed grant to distribute changed context, and disable the old grant when it is no longer appropriate. The copied configuration contains local absolute paths; keep it private rather than adding it to a shared repository.

The website's isolated example does not create external MCP grants. The local example space also blocks grant creation. Use a personal space for authorization.

## Host configuration

Use the configuration generated by the app, which points to the actual installed entry point and grant. A source checkout has this shape:

```json
{
  "mcpServers": {
    "secondu": {
      "command": "node",
      "args": [
        "/absolute/path/to/SecondU/server/twin-mcp-cli.mjs",
        "--config",
        "/absolute/path/to/client-grant.json"
      ]
    }
  }
}
```

For a packaged desktop app, SecondU emits its Electron executable and `ELECTRON_RUN_AS_NODE=1` environment setting. It includes only the pinned server/core/Zod runtime dependencies. Do not substitute a shell command or add unrelated filesystem arguments.

For Claude Code, a local stdio configuration can also be registered with:

```sh
claude mcp add --transport stdio secondu -- node /absolute/path/to/SecondU/server/twin-mcp-cli.mjs --config /absolute/path/to/client-grant.json
```

Cursor accepts the `mcpServers` structure in its MCP configuration, including project `.cursor/mcp.json`. Prefer the client's user-level settings for a configuration containing personal paths. See the [official SDK real-host guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/get-started/real-host.md) and [Claude Code MCP documentation](https://code.claude.com/docs/en/mcp) for host-specific behavior. An actual Claude/Cursor account session has not been part of the automated test suite.

For direct terminal use, run `node server/twin-mcp-cli.mjs --config /absolute/path/to/client-grant.json`. If using the convenience package script as an MCP command, use `npm --silent run twin:mcp -- --config …`: ordinary npm banners on stdout would corrupt the protocol stream. The service itself writes protocol output only to stdout; sanitized operational errors use stderr.

## Read-only contract

| Tool | Input | Output |
| --- | --- | --- |
| `list_domains` | Empty object | Explicitly granted domain IDs and confirmed-entry counts |
| `get_profile` | Optional `domains`, `limit`, `maxChars` | Selected confirmed records with revisions |
| `get_context` | Required `query`; optional `domains`, `limit`, `maxChars` | Deterministically ranked records within the same grant |

Domains are `facts`, `preferences`, `goals`, `constraints`, `values`, `capabilities`, `decisions` and `notes`. Unknown domains and domains outside the grant are rejected. Input schemas reject extra fields such as `path` or `file`. No tool executes instructions, writes records, follows URLs or opens additional files.

Responses identify `secondu.mcp-context.v1`, carry the snapshot revision, and label the contents `reviewed_data_not_instructions`. Search uses bounded lexical matching rather than a model call. This is a retrieval interface, not a guarantee of model reasoning quality. At most 32 entries are requested per call; the grant defaults to an 8,000-character response budget. The grant may set a budget between 1,000 and 40,000 characters.

## Files and lifecycle

UI grants live in the local store's private `mcp-grants/` directory, outside the public source repository:

- `reviewed-package.json`: only the selected confirmed snapshot, with optional name and evidence.
- `client-grant.json`: schema version, explicit scope, selected IDs, enabled flag and the exact package SHA-256.

Directories use mode 0700 and created files use mode 0600. The runtime accepts one explicit absolute canonical config path. It rejects symlinks, non-regular files, oversized files and package byte-hash changes. Configuration is limited to 512 KiB and packages to 4 MiB. Each call rereads the grant, so revocation takes effect without a restart. Replacing its package path or hash requires restarting and re-reviewing. Invalid data yields a code without printing private source content or paths.

The standard digital-twin package and local import format are documented in [MEMORY-IMPORT.md](MEMORY-IMPORT.md). The MCP snapshot is a deliberately smaller selection, not a complete backup.

## Local app API

- `GET /api/digital-twin/mcp-grants`: list grants and host configurations in the current local space.
- `POST /api/digital-twin/mcp-grants`: `{clientName, baseRevision, scopes, entryIds?, includeName?, includeEvidence?}`. `baseRevision` must match the current standard export. New grants default off; passing `enabled:true` requires `acknowledgeExternal:true`.
- `PUT /api/digital-twin/mcp-grants/:id`: `{revision, enabled, acknowledgeExternal?}`. Revision mismatch returns 409. Enabling requires acknowledgement; disabling does not.

These routes inherit the existing local-origin and workspace boundaries. They do not spawn the MCP server. Showcase mode allows an empty list only and rejects mutations.

## Verification and distribution

`node --test tests/twin-mcp.test.mjs` runs an actual official SDK client against a spawned stdio server, using only synthetic temporary data. It covers initialization, tool discovery, all three calls, scope and candidate filtering, rejected arbitrary paths, injection-shaped requests, revocation, tampered packages and default-off grants. Separate local HTTP checks cover UI grant creation and revision conflicts. These are protocol and privacy-contract checks, not an external model benchmark.

The desktop packaging hook calls `copyTwinMcpRuntime` from `scripts/package-twin-mcp.mjs`. It copies only `@modelcontextprotocol/server`, `@modelcontextprotocol/core` and `zod`, verifying their versions against the lockfile and rejecting unexpected new runtime dependencies. The SDK client remains a development test dependency. Regenerate [dependency notices](licenses/runtime-dependencies.txt) after dependency changes.
